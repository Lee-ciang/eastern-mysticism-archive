# SEO Playbook

**Version:** 1.0  
**Project:** Eastern Mysticism Archive  
**KAPF stage:** Performance Validation  
**Document type:** Standard Operating Procedure handbook

## Purpose

This playbook defines repeatable procedures for common SEO situations. Each SOP begins with evidence, produces a documented decision, and ends with validation and monitoring.

Use this handbook together with:

- [SEO Decision Rules](SEO_DECISION_RULES.md)
- [Star Pages](STAR_PAGES_2026-07-24.md)
- [Next Optimization Queue](NEXT_OPTIMIZATION_QUEUE.md)

## Universal Controls

Apply these controls to every SOP:

- Use Google Search Console data before making assumptions.
- Confirm that queries are relevant to the page and project.
- Compare a meaningful date range instead of reacting to one day.
- Record the page, query set, date range, observation, and decision.
- Prefer improving an existing qualified asset before adding content.
- Preserve technical stability, editorial accuracy, and user intent.
- Define a monitoring date before closing the task.

## SOP 1: Google Begins Testing a Page

### Trigger

A page begins receiving relevant Google Search impressions for the first time or after a sustained period with no visibility.

### Objective

Determine whether the page should enter the Star Pages queue and identify the smallest useful optimization.

### Procedure

- [ ] Record the page URL and first observed testing date.
- [ ] Export or record the relevant queries, impressions, clicks, and average positions.
- [ ] Confirm that the queries match the page's intended entity and search intent.
- [ ] Compare the page against competing internal pages for overlap.
- [ ] Review title, introduction, headings, depth, FAQ, and conclusion.
- [ ] Review inbound and outbound contextual internal links.
- [ ] Review the quality and completeness of supporting cluster pages.
- [ ] Identify missing comparison, visual, or related-concept opportunities.
- [ ] Check indexing, canonical behavior, mobile usability, and rendering if a technical concern appears.
- [ ] Add the page to Star Pages Tier C when testing is relevant.
- [ ] Define one focused optimization batch or a monitoring-only decision.
- [ ] Record a follow-up review date.

### Completion Criteria

- Query intent is classified.
- Internal overlap is understood.
- Tier C entry or monitoring status is recorded.
- The next action and review date are documented.

## SOP 2: A Page Suddenly Gains Impressions

### Trigger

Impressions increase materially relative to the preceding comparable period.

### Objective

Determine whether the increase represents a durable opportunity, seasonal event, query expansion, or reporting noise.

### Procedure

- [ ] Confirm that the increase persists beyond a single day.
- [ ] Compare equal periods and account for day-of-week effects.
- [ ] Separate branded and non-branded queries.
- [ ] Identify new queries, countries, devices, and search appearances.
- [ ] Check whether average position changed or query coverage expanded.
- [ ] Confirm that the new queries are relevant and appropriately served by the page.
- [ ] Review recent site, content, linking, or indexing changes that could explain the movement.
- [ ] Check seasonality and festival timing where relevant.
- [ ] Inspect whether another internal page lost impressions for the same queries.
- [ ] Preserve successful intent alignment; do not rewrite immediately without diagnosis.
- [ ] Prioritize low-risk improvements such as clearer sections, useful links, or missing FAQs.
- [ ] Update the Star Page tier or optimization queue when evidence is sustained.
- [ ] Set a monitoring window before evaluating impact.

### Completion Criteria

- The source of growth is classified.
- Cannibalization and seasonality have been reviewed.
- Optimization or monitoring action is recorded.
- No successful section was changed without evidence.

## SOP 3: CTR Decreases

### Trigger

Click-through rate declines for a page, query group, or cluster over a meaningful comparison period.

### Objective

Identify whether the decline comes from ranking mix, query expansion, snippet weakness, SERP change, or intent mismatch.

### Procedure

- [ ] Compare clicks, impressions, CTR, and average position together.
- [ ] Determine whether impressions expanded into lower-ranking queries.
- [ ] Segment by query, device, country, and search appearance.
- [ ] Identify whether rankings remained stable for the core query set.
- [ ] Inspect the current Google result and competing result formats.
- [ ] Review the displayed title, description, breadcrumb, and date information.
- [ ] Confirm that the title accurately matches the strongest intent.
- [ ] Check whether the snippet promises information the page does not deliver.
- [ ] Review structured result eligibility without adding unsupported markup.
- [ ] Avoid sensational or misleading title changes.
- [ ] Define a single snippet or intent-alignment change when justified.
- [ ] Record the change date and allow sufficient time for recrawling.
- [ ] Compare the same query cohort at the follow-up review.

### Completion Criteria

- CTR decline is separated from query-mix effects.
- Any snippet change has an evidence-based rationale.
- The page continues to represent its content accurately.
- Monitoring uses the same relevant query cohort.

## SOP 4: Rankings Improve

### Trigger

Relevant queries move to stronger average positions over a sustained period.

### Objective

Protect the gain, identify supporting causes, and reinforce the cluster without destabilizing the page.

### Procedure

- [ ] Confirm improvement across a meaningful period.
- [ ] Identify the queries, devices, and countries driving the gain.
- [ ] Review whether clicks and qualified impressions increased.
- [ ] Record recent content, linking, visual, or technical changes.
- [ ] Check whether supporting pages also improved.
- [ ] Preserve sections clearly aligned with successful queries.
- [ ] Avoid large rewrites while Google is positively reevaluating the page.
- [ ] Add only missing, high-confidence contextual links or clarifications.
- [ ] Review whether the page should move to a higher Star Page tier.
- [ ] Identify reusable lessons without assuming causation from correlation.
- [ ] Schedule a later review to test durability.

### Completion Criteria

- Improved query groups are documented.
- Successful page elements are protected.
- Tier and queue status are reviewed.
- Lessons are recorded as hypotheses rather than unsupported causal claims.

## SOP 5: Rankings Decline

### Trigger

Relevant query positions or clicks decline materially over a sustained comparison period.

### Objective

Separate normal volatility from technical failure, intent mismatch, competition, seasonality, or content weakness.

### Procedure

- [ ] Confirm the decline using equal date ranges.
- [ ] Segment affected queries, pages, devices, and countries.
- [ ] Check indexing, canonical selection, crawl status, and rendering.
- [ ] Review recent deployments, content edits, and internal-link changes.
- [ ] Check whether another internal page gained the same queries.
- [ ] Inspect search results for intent or feature changes.
- [ ] Review competing pages for genuinely useful coverage differences.
- [ ] Check seasonal demand and news effects.
- [ ] Confirm that the article remains accurate and complete.
- [ ] Identify whether the decline is page-specific, cluster-wide, or site-wide.
- [ ] Fix technical defects immediately when confirmed.
- [ ] For content issues, define a scoped authority improvement rather than adding filler.
- [ ] Record the diagnosis, action, and monitoring period.

### Completion Criteria

- Technical, intent, seasonality, and cannibalization causes are evaluated.
- Remediation matches the diagnosed cause.
- Unrelated content expansion is not used as a default response.
- Follow-up measurement is scheduled.

## SOP 6: When to Optimize an Existing Page

### Trigger

A page shows relevant impressions, ranking opportunity, incomplete intent coverage, weak cluster support, or declining performance.

### Qualification Checklist

- [ ] The page serves a distinct and valuable search intent.
- [ ] Search Console shows relevant testing or historical value.
- [ ] The content has a clear depth, clarity, comparison, FAQ, visual, or linking gap.
- [ ] The gap can be resolved without changing the URL.
- [ ] No other page is a better canonical destination for the intent.
- [ ] The proposed work improves users' understanding.
- [ ] The page belongs to an active Star Page cluster or queue priority.

### Procedure

- [ ] Record baseline performance.
- [ ] Define the exact user and query problem.
- [ ] Audit the page and supporting cluster.
- [ ] Select the smallest coherent optimization batch.
- [ ] Preserve accurate existing material and established intent.
- [ ] Add only verified internal links.
- [ ] Validate links, slugs, orphan status, formatting, TypeScript, and build where applicable.
- [ ] Record the completion date and changed sections.
- [ ] Set a monitoring date.

### Completion Criteria

- The optimization addresses a documented need.
- Technical and content validation passes.
- The change is traceable to a baseline and review date.

## SOP 7: When to Publish New Content

### Trigger

Research or performance data identifies a user need that may require a new page.

### Qualification Checklist

- [ ] Existing successful clusters have received appropriate strengthening first.
- [ ] The proposed entity serves a distinct search and educational intent.
- [ ] No current page can satisfy the intent through expansion.
- [ ] The new page does not create a duplicate slug or near-duplicate topic.
- [ ] A hub, inbound links, outbound links, and cluster role are defined.
- [ ] Evidence supports the priority through Search Console, audience research, or a documented knowledge gap.
- [ ] The project has capacity to review and maintain the asset.

### Procedure

- [ ] Write the entity definition and scope boundary.
- [ ] Identify the target cluster and authority page.
- [ ] Map required relationships before drafting.
- [ ] Check all candidate slugs across the archive.
- [ ] Define content, evidence, accessibility, and visual requirements.
- [ ] Produce the page using the established archive format.
- [ ] Validate duplicate slugs, links, orphan status, and build.
- [ ] Record the publication date and monitoring window.

### Stop Conditions

Do not publish when:

- An existing page already serves the intent.
- The topic is justified only by content-volume goals.
- No meaningful inbound relationship exists.
- The page would fragment a successful authority topic.
- Review or maintenance capacity is unavailable.

## SOP 8: Monthly SEO Review

### Trigger

The scheduled monthly Performance Validation review.

### Preparation

- [ ] Create or open the relevant `docs/seo/reports/YYYY/MM/` workspace.
- [ ] Select comparable date ranges.
- [ ] Export or record page and query performance.
- [ ] Gather the previous queue, Star Page tiers, and completed-change log.

### Review Procedure

- [ ] Record total clicks, impressions, CTR, and average position.
- [ ] Identify the largest relevant page and query gains.
- [ ] Identify the largest relevant declines.
- [ ] Review Tier A and Tier B Star Pages individually.
- [ ] Identify new pages receiving relevant impressions.
- [ ] Add qualified emerging pages to Tier C.
- [ ] Review CTR changes separately from ranking changes.
- [ ] Check for internal query overlap or cannibalization.
- [ ] Review completed optimizations against their baselines.
- [ ] Check indexing and technical health indicators.
- [ ] Review whether cluster support, visuals, or FAQs remain weak.
- [ ] Reorder the optimization queue only when evidence supports it.
- [ ] Select the next small set of measurable actions.
- [ ] Record risks, assumptions, owners, and follow-up dates.

### Monthly Deliverables

- [ ] Completed monthly report.
- [ ] Updated optimization queue or confirmation that it remains valid.
- [ ] Star Page tier changes, if any.
- [ ] A short list of approved optimization actions.
- [ ] Monitoring dates for recent changes.

## SOP 9: KAPF Decision Workflow

### Purpose

Use this SOP to determine which KAPF layer needs work before approving an SEO task.

```text
Knowledge
    ↓
Authority
    ↓
Performance
    ↓
Flywheel
```

### Knowledge Check

- [ ] Does the correct entity page exist?
- [ ] Is its scope distinct?
- [ ] Is the slug stable and unique?
- [ ] Does it belong to a coherent cluster?
- [ ] Are important relationships represented?

If any answer is no, resolve the knowledge-model problem before performance optimization.

### Authority Check

- [ ] Is the hub comprehensive and accurate?
- [ ] Are supporting pages strong enough?
- [ ] Are internal links useful and contextual?
- [ ] Are comparisons, FAQs, and visuals serving real user needs?
- [ ] Is the cluster free from damaging overlap?

If authority is weak, strengthen the existing cluster before expansion.

### Performance Check

- [ ] Is Search Console testing the page for relevant queries?
- [ ] Is there a measurable opportunity or problem?
- [ ] Is the proposed action connected to observed evidence?
- [ ] Is a baseline recorded?
- [ ] Is a review date defined?

If evidence is insufficient, monitor rather than making a large change.

### Flywheel Check

- [ ] Has the knowledge asset demonstrated stable value?
- [ ] Can it support reusable diagrams, social assets, lessons, or other formats?
- [ ] Will reuse preserve accuracy and source relationships?
- [ ] Can results feed back into the knowledge system?

Move into flywheel activity only after knowledge, authority, and performance are sufficiently validated.

### Decision Record

Every approved action should record:

- KAPF layer.
- Evidence reviewed.
- Page or cluster.
- Problem statement.
- Approved action.
- Validation requirements.
- Completion date.
- Monitoring date.
- Outcome when available.

## Validation Standard

When an SOP results in repository changes, apply validation proportionate to scope. Content work normally requires:

- Duplicate slugs: 0.
- Broken related links: 0.
- Broken body links: 0.
- Orphan pages: 0.
- `git diff --check`: passed.
- Production build: passed.
- TypeScript: passed.
- Static generation: passed.

Documentation-only changes require file-existence and internal-document-reference checks. They do not require a production build unless documentation tooling is part of the build.

## Version Maintenance

Update this playbook when a recurring SEO situation requires a stable new SOP or an existing procedure repeatedly fails to produce a clear decision.

Record material process changes through a new version. Do not rewrite monthly evidence or dated Star Page snapshots to make them match later conclusions.
